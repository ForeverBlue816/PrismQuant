# FlatQuant native INT4 build for A40

Final runtime uses the existing Python3.11 interpreter only; its Torch/CUDA/FlashAttention packages are isolated in `/projects/nar/nar-validation/flatquant-native-runtime/packages`, with the separate TF4.45 overlay and untouched official source clone. Source `environment_torch26.sh` before invoking `/projects/nar/nar-validation/e28-env/bin/python`. No shared package environment or original upstream checkout was modified.

`build_torch26.sh` compiles unchanged official `deploy._CUDA` and the pinned FHT kernels against **Torch2.6.0+cu124**, targeting **SM86 only**; CUDA compiler12.4.99 comes from the cluster module installation. Parallel build workers are capped at2. The earlier `FlatQuant-native-cu124` tree is a separate Torch2.4 compatibility build and must not be used with this final Torch2.6 runtime.

The official FlatQuant commit is `9d88ffcb7d2c6bda59fb5c44dad36adc101aadb1`; CUTLASS is `ad7b2f5e84fcfa124cb02b91d5bd26d238c0459e`; FHT is `d1a56eee9d502e67faacf61b7b947180d66b32a0`. FlashAttention2.7.4.post1 is the official cu12/Torch2.6/ABI-false CPython3.11 wheel; Triton is3.2.0.

`check_runtime.py` imports the CUDA bindings directly without executing GPU operations and records binary/source hashes in `native_runtime_manifest.json`. Full `deploy` import on a CPU login node encounters Triton3.2's CUDA-driver initialization in its autotune decorator; this CPU-only import limitation does not apply to an allocated A40. Brief deterministic GPU smoke in existing job1736285 step4 passed full TF4.45 native model-module import, signed INT4 GEMM, symmetric quantization, source-exact dequantization, and pinned FHT128. The step exited and released its GPU. No full model, timing benchmark, or random-weight/FP16 performance run was executed.

Llama3.2-3B's3072 hidden dimension is outside the official README's documented power-of-two condition; this is a documented support limitation, not an observed GPU failure. Native backend semantics also differ from fake-quant accuracy (including prefill K/V behavior), so its real exported checkpoint requires a separate PPL measurement before claiming joint accuracy and speed. The parent owns export/measurement runners and scheduling.

The unchanged official `deploy/kernels/quant.cu` computes `int_to_half(q / 10.0f)`; its helper first casts to `int` (truncation toward zero), clamps to ±65176, converts to half, then the kernel applies half-precision row/column scale products and multiplies by10. On the deterministic tiny smoke input, dequantization matches this source arithmetic exactly but differs from ideal `q * row_scale * col_scale` in476/512 values, maximum absolute difference1.125. These are tiny kernel values, **not model logits or PPL**. `native_gpu_smoke_1736285_source_semantics.json` preserves the GPU evidence; the original ideal-equality failed smoke is preserved separately. Do not silently patch this numerical behavior or infer algorithm quality from the kernel-level discrepancy.
