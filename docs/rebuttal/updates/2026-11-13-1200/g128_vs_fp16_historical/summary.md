# Meta-Llama-3.1-8B — historical g128 asymmetric A4 / GPTQ W4 / simulated KV4 versus FP16

Job 1734010 already measured all three rows on the same exclusively used NVIDIA A40 on 2026-11-11. This report exposes those existing measurements rather than labeling them as a new experiment. PrismQuant k=8 takes 13225.179 ms for prefill and reaches 0.377550 decode tokens/s: respectively 33.967x and 87.568x slower than the historical FP16 backend. Hadamard is 34.878x/97.125x slower. These results provide the missing measured prototype-to-FP16 ratio; they do not support an acceleration claim. [Complete table](table.md), [machine-readable comparison](comparison.json).

The actual quantized format is the E14 `default` GPTQ protocol: signed symmetric W4 with one recovered FP32 scale per output channel, asymmetric A4 in 128-channel groups with FP16 scale and minimum offset, and floating KV4 simulation with token-group 32 K, channel-group 128 V and residual 32. The weights are stored as packed nibbles plus per-group INT32 code sums. All 224 exported projection matrices reconstruct their saved BF16 values exactly, but arithmetic uses unrounded FP32 weight reconstruction rather than every BF16 QDQ reconstruction residual. Here **g128 asymmetric describes activations; it does not mean group 128 asymmetric weights**. `nar/e38_8b_integer.py` loads `protocol='default'`; `PackedSymmetric4.integer_from_metadata` in `nar/e38_integer_operator.py` repeatedly expands each group to INT8, calls `torch._int_mm`, and applies FP32 scale/offset corrections. Decode pads M=1 to 32; Python launches, unpacking and group temporaries are included. It is a runnable INT8 arithmetic prototype with W4 storage, not native packed-INT4 Tensor Core inference; KV is not packed.

The numerical check and timing reuse the same loaded model within each row. The reference and integer paths share the quantized checkpoint; reference linear weights are removed before timing. FP16 is a separate model using the original base snapshot, cast from BF16 to FP16, while both quantized prototypes retain BF16 residual/nonlinear operations. Base revision is `e9a141a2091ea561b96483212645a2a05e6f99fc`; the quantized snapshot is `fc812e6687165115feee00293c953a1b521d3bd0`. Actual recorded repository HEAD is `79c2e4caadcb36ec7b612542cadb56fd4b4b13a0`, distinct from the requested source-commit label `9a1bade02df471d25c4cf04e88ae83468175772a`; source-file hashes are retained in comparison.json and the original records.

The timing workload is matched at batch 1, 2048 prefix tokens, fixed decode token 100, 128 decode steps with the first 8 excluded, last-position logits, 10 warmups and 20 measured repetitions. Both use synchronized eager wall time. All recorded GPU exclusivity checks pass on `GPU-02833fb5-df29-3b93-e608-b64499c0ae93`; the rows execute sequentially, not in one shared Python/model instance. Ratios compare medians and are descriptive; no paired timing confidence interval is claimed.

The old cache boundary differs. FP16 creates one native paged cache for a workload and reuses it, clearing it before each timer. The prototype creates a fresh Transformers DynamicCache before every timer; tensor allocation/growth occurs inside the timed forward. Thus both exclude cache-object construction, but only FP16 preallocates and reuses the actual storage. Prefix preparation and the first 8 decode steps are outside the decode timer in both paths. These historical numbers must not be mixed silently with new fresh-cache timings that include cache creation in prefill. PyTorch peak allocation/reservation includes all resident model/cache/temporary allocations; the decode peak also includes untimed prefix preparation. Prototype memory savings cannot be attributed to packed KV.

The software stacks also differ: FP16 uses torch 2.4.1+cu124, CUDA 12.4, transformers 4.36.2, triton 3.0.0 and flash-attn 2.6.3 in `e28-env`; the g128 prototype uses torch 2.11.0+cu128, CUDA 12.8, transformers 5.16.0.dev0 (commit `a353632607c59463e6ced86a44c2de3c2cd62d5e`) and triton 3.6.0 in the main validation environment. The shared job/GPU controls hardware placement, not architecture/cache/software differences, so this is not an isolated kernel-only quantization speedup estimate.

The reference/prototype PPL differences are small (PQ -0.00116611, Hadamard +0.00217191), but maximum logit differences are 28.0/27.0625 and argmax agreement is 86.9130%/85.3055%. These are explicitly preserved as numerical limitations; no threshold is used to suppress timing. PPL uses the same 141 WikiText2 windows as the raw equivalence records. Eight-task results are outside this historical timing report.

A possible next optimization is a tiled fused Triton **INT8** grouped computation: retain exact activation metadata, unpack W4 within a tile, compute INT8 products with INT32 group accumulators, apply FP32 per-group scale/offset terms, and reduce across groups without Python dispatch per group. This has not been implemented or timed. It would still be INT8 compute, and would not solve packed KIVI cache deployment. Existing native QuaRot signed-INT4 GEMM only exposes a full-K integer dot followed by row/output scaling; g128 activation scales vary along K, so a genuine native-INT4 g128 backend requires additional group-aware integration. No new CUTLASS/PTX implementation is claimed here.
